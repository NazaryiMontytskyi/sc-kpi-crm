# ADR-0010: Task assignment model and migration of resolutions

- Status: Accepted
- Date: 2026-11-16

## Context
`TASK_TRACKING_FEATURE.md` retires the `Resolution` mechanism (author -> executor + co-executors, fixed lifecycle, redirect chains, completion note, rework) and moves "who does what by when" onto the plain `Task`. Its §3 lists the intentional conflicts with `CONTEXT.md` (§3 glossary, §4 domain model, §5.2 permissions, §5.3 "no task hierarchy" and the resolution lifecycle); until a human updates `CONTEXT.md`, the feature file wins for those items only. Existing resolution data must be migrated, not dropped (§5.8), and history is never rewritten. This ADR records the model decisions (§6.1) taken in INC-071; the conversion itself is INC-072, the endpoints INC-073..076, the removal of resolutions INC-081..082.

## Decision
- **Task fields.** `task` gains `creator_id` (NOT NULL), `issued_at` (NOT NULL, UTC instant), `parent_task_id` (nullable self-reference) and `version` (optimistic locking). The former `due_date` column is **renamed** to `deadline` (V25; values are preserved by the rename, the index becomes `ix_task_deadline`); it stays a `DATE` that is due at the end of that day in `Europe/Kyiv`. Existing rows are backfilled: `creator_id = created_by` (the nil system actor when `created_by` is NULL) and `issued_at = created_at`. The API exposes `deadline`, `issuedAt`, `creatorId`, `parentId`, `version`; `authorId` stays for compatibility and equals `creatorId`.
- **Subtask depth = 1** `[ASSUMPTION]`. A subtask is a `Task` with `parent_task_id` that inherits the parent's `space_id`; a subtask cannot have subtasks. The database only guarantees "not its own parent" (`ck_task_not_own_parent`); the depth rule, the space rule and the deadline rule (subtask deadline <= parent deadline for new edits; a parent without a deadline imposes no limit) are enforced by the service with pure, unit-tested rules (INC-074). Migrated subtasks are **not** clamped to the parent deadline.
- **Shared status** `[ASSUMPTION]`. A task has one status (a `SpaceStatus`) shared by all assignees. **Extension point:** an assignee is a row of its own (`task_assignee`, entity `TaskAssignee`), not a user-id collection on the task, so a per-assignee state column can be added later without reshaping the task API.
- **Assignees.** `task_assignee(id, task_id, user_id, assigned_by, assigned_at, removed_at, removed_by, audit columns)`. Unassigning sets `removed_at` (row kept). A user is an active assignee of a task at most once: partial unique index `uq_task_assignee_active (task_id, user_id) WHERE removed_at IS NULL`; "my tasks" lookups use `ix_task_assignee_user (user_id, task_id)`. `assigned_by` has no foreign key (the system actor is the nil UUID, as in `resolution_history`).
- **Artifacts.** `task_artifact(id, task_id, artifact_type FILE|LINK, file_id -> file_object, url (<= 2048, http/https only), title, added_by, added_at, audit + archive columns)`. Exactly one of `file_id`/`url` is set, matching the type (check constraints). Removing an artifact archives the row; the file stays in storage (ADR-0005). `Task.attachmentIds` (`task_attachment`) are converted to FILE artifacts in the artifacts increment (INC-075).
- **Reminders.** `task_reminder(task_id, user_id, threshold, deadline, sent_at)` with primary key `(task_id, user_id, threshold, deadline)`: at most one notification per task, recipient, threshold and deadline; a changed deadline re-arms the reminders. It replaces `resolution_reminder` from INC-076 on.
- **Permission `tasks.assign`** (group Tasks). Assigning or creating work **for another user** requires it; working for oneself needs only `tasks.create`. Migration V26 grants `tasks.assign` to every role (archived ones included) that holds `resolutions.create`; the template roles seed grants it to every template role that had `resolutions.create` (Head, Deputy Head, Head of Department, Head of Division, Member, HR); **Advisor does not get it**. Admin has every key by definition. `resolutions.create`/`resolutions.redirect` stay in the catalog until resolutions are removed (spec RR-3), when a later migration deletes their role rows.
- **Optimistic locking.** `Task` carries a JPA `@Version`. Update and status-change requests accept the `version` the client last read; a mismatch is rejected with 409 `TASK_VERSION_CONFLICT` (RFC 7807). The field is optional in this increment so existing clients keep working; the tracker UI sends it from INC-077 on and shows a reload hint on 409 `[ASSUMPTION]`. Writers keep the existing row lock (`lockById`), so the explicit comparison is the conflict check.
- **Migration mapping of resolutions** (INC-072, spec §5.8). Each resolution becomes **one subtask** of its task, in one transaction, deterministically:
  - executor and co-executors -> `task_assignee` rows (`assigned_by` = author, `assigned_at` = resolution creation time);
  - author -> subtask `creator_id`; instruction -> subtask description; due date -> subtask `deadline` (not clamped);
  - state -> the first active status (lowest position) of the target category in the parent's Space: NEW -> TODO; IN_PROGRESS, REWORK, SUBMITTED -> IN_PROGRESS (SUBMITTED is flagged by a comment); ACCEPTED -> DONE; CANCELED, REDIRECTED -> CANCELED `[ASSUMPTION]`. **Fallback** when the Space has no active status of that category: the first active status of the nearest category in the order IN_PROGRESS -> TODO for IN_PROGRESS, CANCELED -> DONE for CANCELED, and the first active status of the Space otherwise; the original state is always recorded in the marker comment;
  - completion note, rework comments and history entries -> comments on the subtask with the original author and timestamp, prefixed with a localized marker;
  - redirect chains -> flat sibling subtasks plus a "Redirected from X" comment on the child (no subtask of a subtask);
  - sent `resolution_reminder` rows -> `task_reminder` rows (every recipient of the old job, see "Conversion as implemented"), so nothing is sent twice after cut-over.
- **Conversion as implemented** (INC-072, `V28__tasks_resolutions_to_subtasks.sql`). Decisions taken during implementation, refining the mapping above:
  - **Plain SQL, Java specification.** The conversion is a SQL migration so it never depends on application code that is deleted with the resolutions (a Java migration would have to stay forever, and spec §9.1 removes every `Resolution*` class). The pure class `tasks.internal.ResolutionMigrationMapping` is its executable specification; an integration test runs V28 on fake data and asserts that every written row equals the mapping's output. When resolutions are removed (INC-081) the class and its tests may be deleted; V28 stays untouched.
  - **Ids.** The subtask keeps the resolution's id (old links and audit rows stay traceable). Assignee and comment ids are `md5('resolution-migration:' || key)::uuid`, so the conversion is deterministic.
  - **Title** = first non-blank line of the instruction (trimmed), at most 200 characters with an ellipsis; fallback "Резолюція". Priority NORMAL, no labels or custom fields. Audit columns and the archive state are copied from the resolution (an archived parent task archives the subtask too).
  - **Status tie-break and last resort.** Equal positions are ordered by id; a Space without any active status keeps the parent task's status.
  - **Comments.** Per resolution: one summary comment by the system actor (nil UUID) at the resolution's last update, recording the original state (SUBMITTED flagged as awaiting acceptance); one comment per history entry (actor, time, transition, cascade note, the entry's comment labelled as completion note for SUBMITTED, rework comment for REWORK); a completion note no SUBMITTED history entry carries (defensive) by the executor; "Redirected from «X»" by the child's author at its creation, X = the title of the sibling subtask it came from. Count = resolutions + history entries + orphan notes + redirected children.
  - **Marker texts are stored in `uk`** (no request locale in a migration); keys `tasks.migration.resolution.*` exist in uk and en and are mirrored as literals in V28.
  - **Reminders.** Each sent `resolution_reminder` row becomes a `task_reminder` row for every recipient of the old job: the executor, every co-executor and, for `OVERDUE`, the author (matches NT-2), keyed by the reminder's due date. Threshold names (`DUE_SOON`, `OVERDUE`) are copied unchanged; INC-076 must treat them as already sent.
  - **No audit rows** are written for migrated data (none were required); existing audit rows are untouched. Resolutions created after V28 runs are not converted.
- **Legacy tables are retained** `[ASSUMPTION]`: `resolution`, `resolution_co_executor`, `resolution_history`, `resolution_reminder` stay **read-only for one release**; nothing writes to them after cut-over and nothing hard-deletes them. Dropping them is a later migration decided by a human. Past audit rows about resolutions are never rewritten. Existing migrations (V16, V23) are never edited.
- **Subtasks as implemented** (INC-074; pure rules `SubtaskRules`, `SuggestCloseRule`; no schema change).
  - **Creation** only through `POST /tasks/{id}/subtasks` (`tasks.view` + `tasks.create`); the subtask takes the parent's space, the caller is its creator. `assigneeIds` omitted = for the caller; an empty list = unassigned; anybody else needs `tasks.assign` (same rule as `AssigneeRules`). Events: `CREATED` and `ASSIGNED` on the subtask, `SUBTASK_ADDED` (with `subtaskId`) on the parent.
  - **Deadline rule** is checked only when a deadline actually changes (create, or an edit with a different deadline), so edits that keep the deadline never fail on migrated subtasks. Moving a parent deadline reports every non-archived subtask (any status) left later than it (422 `TASK_DEADLINE_BEFORE_SUBTASKS`, property `conflictingSubtasks`); a violation that already existed before the move (migrated data) is tolerated when the parent deadline moves later, because that move makes nothing worse. Writers that check the rule lock parent before subtask.
  - **Archive cascade.** Archiving a task archives its non-archived subtasks with the **same instant (microsecond precision) and actor**. Restoring a task restores only the subtasks whose `archived_at`/`archived_by` equal the parent's, i.e. those archived by the cascade; subtasks archived on their own before stay archived. A subtask cannot be restored while its parent is archived (409 `TASK_PARENT_ARCHIVED`). V28 copied the parent's archive columns to subtasks of archived parents, so they come back with the parent too.
  - **Suggest close** is computed per read (no stored flag): true when the task is not in a DONE/CANCELED-category status and at least one non-archived, non-canceled subtask exists and all of those are DONE-category. The DTOs expose `subtaskCount`, `openSubtaskCount` and `suggestClose`; nothing changes the parent automatically and closing it with open subtasks is allowed. The legacy `suggestDone` stays until INC-081.

## Consequences
- `task.due_date` no longer exists; any native SQL must use `deadline`. The task list sort key is `deadline` (was `dueDate`); the `dueFrom`/`dueTo` filters keep their names until the filter rework (INC-073).
- Task audit snapshots now contain `deadline`, `issuedAt`, `creatorId`, `parentId` and `version` (instead of `dueDate`).
- Until INC-073/074/075 ship, the new tables exist but are not written by the application.
- The role builder lists `tasks.assign` next to the resolution keys; the duplicate wording disappears with RR-3.
